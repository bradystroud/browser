# browser

A macOS browser: Chromium (via CEF) rendering inside a native Swift/AppKit shell, with first-class profiles and rule-based link routing (open a link in a specific profile based on domain and/or source app).

## Architecture (decided — don't change these without a strong, stated reason)

- **Engine:** CEF (Chromium Embedded Framework), Chrome bootstrap (the only bootstrap since M128), **Alloy-style** browser windows parented into our own `NSView` via `CefWindowInfo.SetAsChild` + `runtime_style = CEF_RUNTIME_STYLE_ALLOY`. Chrome-style windows in native NSWindows are unsupported on macOS — do not attempt it.
- **Layering:** Swift/AppKit UI (tab strip, omnibox, settings) → thin Obj-C++ (`.mm`) bridge exposing Obj-C interfaces → CEF C++ API (`libcef_dll_wrapper`). No CEF types leak into Swift.
- **Engine-agnostic UI (standing principle):** UI/shell code must treat the engine as swappable — both CEF and WebKit run in every launch, and each tab picks one. New UI code programs against `BrowserEngine`/`EngineTab`/`EngineTabDelegate` (`Sources/App/Engine/BrowserEngine.swift`), never against a `BRW*` Obj-C bridge type directly — those are confined to the adapter (`Sources/App/Engine/CEFEngineAdapter.swift`, `CEFEngine`/`CEFTab`, referenced elsewhere only through the `Engines` facade in `Sources/App/Engine/Engines.swift`). Grep gate: `grep -rn "BRW" Sources/App --include="*.swift"` should only match `Engine/` files, documentation comments pointing at bridge internals, the injected JavaScript's own `BRWNotification` name in `NotificationOverrideScript.swift`, and the `BRWBuild*` Info.plist key names in `DevBuildIndicator.swift` (not real code dependencies). Engine-specific behavior, flags, and workarounds live behind the bridge, not in Swift. If a feature seems to need CEF details in UI code, extend the bridge interface instead. **What differs between engines is declared, not detected:** UI reads the tab's own `Tab.capabilities` (`EngineCapabilities` — in-app DevTools, docking, whether docked tools draw their own dock/close controls, responsive design, per-tab mute/CPU, custom context-menu items, native swipe navigation) to decide what to offer, and never asks which engine is running. Two tabs side by side can disagree, so there is no process-wide value; only process-wide UI (the Extensions menu) asks `Engines.anyEngine(\.x)`.
- **Profiles:** one `CefRequestContext` per profile, each with its own `cache_path`; **all cache paths must live under the shared `CefSettings.root_cache_path`** (CEF crashes otherwise).
- **Link routing:** app registers as default browser (`kAEGetURL` Apple Event); sender app resolved via `keySenderPIDAttr` → `NSRunningApplication`. Rules: domain glob + URL regex + source bundle ID, AND across present fields, first match wins. With no match, the link opens in the frontmost non-private window's profile, and with no window open, in the configured fallback profile (`ProfileManager.fallbackProfile`). There is no special "default" profile: a fresh install starts with `Personal`, and nothing creates a profile by a hardcoded name.
- **Distribution:** Developer ID + notarization only. **Never App Sandbox** — sandboxing breaks default-browser registration. No Mac App Store.
- **Passkeys:** QR/hybrid + security keys work via Chromium's stack; Touch ID / iCloud Keychain requires Apple's restricted `com.apple.developer.web-browser.public-key-credential` entitlement, which Apple granted for `dev.stroud.browser`. It is authorized by a Developer ID provisioning profile kept outside this repo at `~/.config/browser/Browser.provisionprofile` (override with `BRW_PROVISIONING_PROFILE`). `scripts/sign.sh` embeds it and adds the restricted keys to the main app only, read from the profile itself. Ad-hoc builds get neither, because a restricted entitlement without a matching embedded profile is killed at launch. `scripts/release.sh` refuses a real-identity release with no profile. Apple's grant also commits us to iCloud Keychain passkeys for both sign-in and saving new ones. **With the entitlement, the WebKit engine gets Touch ID / iCloud Keychain passkeys for free** (confirmed on GitHub sign-in). **The CEF engine does not, and cannot without a from-source CEF build:** Chromium does check the entitlement, but it only starts its iCloud Keychain authenticator when it can find the tab's `NSWindow` through a Chromium `views::Widget` (`ChromeAuthenticatorRequestDelegate::ConfigureNSWindow`). An Alloy browser parented into our own `NSView` has no widget, so Chromium silently falls back to QR/hybrid and security keys. **So CEF tabs get the system sheet from the app instead** (`Sources/App/Passkeys/`): `PasskeyPageScript` replaces `navigator.credentials.get`/`create` for `publicKey` requests in the main frame and sends them over `cefQuery` to `PlatformPasskeyBroker`, which calls the AuthenticationServices API Apple provides for browsers (`ASPublicKeyCredentialClientData`, macOS 13.5+; security keys 14.4+). That API also needs the user's per-app permission (`kTCCServiceWebBrowserPublicKeyCredential`, asked for with `ASAuthorizationWebBrowserPublicKeyCredentialManager.requestAuthorizationForPublicKeyCredentials`): until it is granted, `AuthenticationServicesAgent` refuses every iCloud Keychain request before any sheet, and the page sees only `NotAllowedError`. WebKit's own passkey path does not need it, so a working WebKit sign-in proves nothing about CEF tabs. A scratch instance started from a shell is attributed to the terminal app by TCC, so its prompt names the terminal, not Browser. **The agent also allows this app only one passkey request at a time**, because it is not a registered web browser to the agent (that needs `com.apple.developer.web-browser`, which the profile does not grant): `ASCAuthorizationTrafficController` keeps the open request per app ID, and refuses every new one (`AuthorizationError Code=1`, "Told not to present authorization sheet", for WebKit tabs too) while an entry exists. An entry whose app was killed mid-request stays until `AuthenticationServicesAgent` restarts (`kill -9` it as the user, since SIP blocks `launchctl kickstart`; launchd starts it on demand). So `PlatformPasskeyBroker` ends its request on quit, and a scratch test must end its request (an `AbortSignal`) before it kills the instance. **That API signs whatever origin and RP ID it is given**, so the broker uses only the engine-derived `PageMessage.origin`, and `WebAuthnPlanner` (WebEngineCore) accepts an RP ID only when it is the origin's host or a registrable suffix of it, checked against the real Public Suffix List (`public_suffix_list.dat`, vendored, refreshed by `scripts/update-public-suffix-list.sh`; never `RegistrableDomain`, which is a heuristic). Only the selected tab of the key window may raise the sheet. Subframes, conditional (autofill) and silent mediation, and unmodelled extensions fall through to Chromium's own flow, as does everything when the entitlement is missing (an ad-hoc build). **WebKit is the default engine** when neither `--engine` nor Settings chooses one (`EnginePreference`): it reaches the sheet with no app code in the path, and a CEF tab on macOS before 13.5 or in an ad-hoc build still gets no Touch ID prompt and no error.

## UI verification protocol (Brady tests, agents don't drive his machine)

Do NOT drive the app's UI with osascript/System Events/keystroke automation — it's flaky here, interferes with Brady's own use of the app, and he prefers testing UI himself. Agents verify what's verifiable non-interactively (build green, unit tests, code review of the key path, log output), then END their report with a manual test hand-off in exactly this shape:

**Test:** (numbered steps — what to do)
**Expect:** (what should happen at each step)
**Report:** (what to tell us, especially the failure signals to look for)

Launching the app to confirm it starts, and reading logs/crash reports, is fine. Screenshot-only passive capture is fine. Sending synthetic clicks/keystrokes is not.

## Conventions

- **Never `pkill -f` a browser process.** `pkill -f "Browser.app/Contents/MacOS/Browser"` also matches Brady's real running `/Applications/Browser.app` and will kill his live session. Capture your own test launch's PID and kill exactly that. The one sanctioned exception is `scripts/install.sh`, where terminating the installed app is the point.
- **Never launch a scratch test instance with `open build/.../Browser.app --args ...`.** The test build shares a bundle identifier with the installed `/Applications/Browser.app` -- if Brady's real app is already running, macOS's `open` just activates his existing window (silently ignoring your `--args`) instead of spawning a new process; a PID grabbed afterward may be his real session, not yours, and a screenshot against it captures his actual browsing.
- **Launch scratch instances with `scripts/launch-scratch.sh <profiles-root> [-- <extra args...>]`, not by execing `build/Sources/App/Release/Browser.app/Contents/MacOS/Browser` directly.** That shared build output path is also what a concurrent `./scripts/build.sh` re-signs as its last step -- if your scratch instance is still running from that exact path when another agent's build finishes, the kernel's code-signing enforcement SIGKILLs it the instant its backing pages are rewritten, with no crash report, and this has repeatedly been misdiagnosed as flaky host/environment load rather than this race. `launch-scratch.sh` copies the built bundle (`ditto`, `codesign --verify --strict` on the copy) to a private `/tmp` location first and execs from there, so a later build can never touch it -- e.g. `./scripts/launch-scratch.sh /private/tmp/my-test -- --profile default --test-no-activate --show-settings-tab general &`, capture `$!` exactly as before (the script `exec`s the real binary as its last step, so `$!` is already that process's real PID -- `scripts/shot-window.sh` works unchanged against it). See the script's own header comment for the full usage.
- **Shared-tree commits:** multiple agents work in this tree concurrently. Always commit with explicit paths (`git commit -m "..." -- <your files>`) — never bare `git commit` (it sweeps whatever anyone else has staged) and never `git add -A`/`git add .`.
- **Explicit paths are not enough when the file itself is shared.** `git commit -- <paths>` commits the **working tree** for those paths and ignores the index, so committing "your" file also commits any *other* agent's uncommitted hunks sitting in it. This has already happened once: a commit scoped to one agent's own paths swept another's in-flight omnibox change out of `BrowserWindowController.swift`, and was only caught by reading the commit afterwards. Explicit paths protect you from committing other *files*, not from committing other people's *changes inside your files*. When a file you're committing is dirty with someone else's work, stage only your own hunks (`git add -p`, or `git apply --cached` on a filtered patch) and then commit with **no paths at all**, so it uses the index. Always read `git show --stat` (and, for a shared file, the diff) after committing.

- **Plans, research and per-task notes are short-lived and do not live in this repo.** Write them where the work happens and let them go; anything that stays true belongs in this file (see "Hard-won engine facts"), and the issue history belongs in beads. This repo is public — nothing personal, client-related, or screenshot-of-a-real-desktop goes in it, ever.
- CEF binary distributions are large; they live under `third_party/cef/` and are gitignored — `scripts/fetch-cef.sh` downloads the pinned version (currently 150.0.14, macOS arm64 Standard distribution).
- **Sparkle** (auto-update, browser-wc7) is fetched the same way: `scripts/fetch-sparkle.sh` puts the pinned version (2.9.6) in the gitignored `third_party/sparkle/`, and `scripts/build.sh` runs it for you. Unlike CEF it is a *compile-time* dependency (`import Sparkle`), so a bare `cmake` without it fails the configure step outright. The app-side wiring is `Sources/App/Update/UpdateCoordinator.swift`; the release-side appcast generation is `Packages/UpdateCore` + `scripts/release.sh`. See `docs/auto-update.md` — it includes the one-time EdDSA key generation, which is a human action and has not been done yet.
- The link-routing rule model + matcher (`RoutingRule`/`RuleMatcher`) live in `RoutingCore/`, a standalone SwiftPM package with its own unit tests (`cd RoutingCore && swift test`) so the matching logic can be tested independent of the full CEF/Xcode app build. `Sources/App/CMakeLists.txt` compiles those same source files directly into the Browser executable — one copy of the logic, two ways to build it.
- Per-profile history/bookmarks/downloads (`HistoryStore`/`BookmarkStore`/`DownloadStore`) live in `Packages/BrowserCore/`, a standalone SwiftPM package with its own unit tests (`cd Packages/BrowserCore && swift test`), same "one copy of the logic, two ways to build it" pattern as `RoutingCore/` above — `Sources/App/CMakeLists.txt` compiles those same source files directly into the Browser executable.

## Skills

This repo's skills live in **`.agents/skills/<name>/SKILL.md`**, and `.claude/skills` is a symlink to that directory. `.agents/` is the source of truth; every tool's own directory points at it rather than holding a second copy that can drift.

That location is what makes one skill work in every tool: Codex scans `.agents/skills` in each directory from the working directory up to the repo root, and Claude Code reads `.claude/skills` — which is the same files through the symlink. Add a new skill under `.agents/skills/`, never under `.claude/skills/`.

- `ship` — build, install to `/Applications/Browser.app`, relaunch.

## Build & run

```
./scripts/build.sh            # fetch-cef.sh (if needed) -> cmake -G Xcode -> build -> sign inside-out
./scripts/launch-scratch.sh /private/tmp/my-test -- --profile default   # never `open` the build: see Conventions
```

`scripts/build.sh` always builds the Release configuration; pass `Debug` as `$1` to build that instead. Signing auto-detects a real "Developer ID Application:" identity in the keychain (`security find-identity -v -p codesigning`) and uses it when present — falling back to ad-hoc (`CODESIGN_IDENTITY=-`) otherwise, e.g. a from-scratch clone with no cert yet — an explicit `CODESIGN_IDENTITY` always overrides the auto-detection (browser-35t). A real-identity build also gets a `BRWDisableMockKeychain` Info.plist key, so a released install uses genuine Keychain-backed cookie encryption while dev builds keep `--use-mock-keychain`.

**Dev-build banner:** any build not running from exactly `/Applications/Browser.app`, or launched with `--profiles-root`, shows an amber `DEV BUILD` strip atop every window (bundle path, commit/branch from the `BRWBuild*` Info.plist keys `scripts/stamp-build-info.sh` writes before signing, engine, profiles root) and a `DEV` Dock badge. `--dev-banner on|off` forces it either way. See `Sources/App/DevBuildIndicator.swift`.

## Hard-won engine facts (read before touching the relevant code)

Working notes for individual tasks are deliberately not kept in this repo — they're short-lived, and the beads tracker holds the issue history. What survived from them, because getting it wrong costs a day:

- **`BRWMessagePump`:** `OnScheduleMessagePumpWork` must *unconditionally* defer to a fresh run-loop turn, matching CEF's Mac-specific reference pump rather than the shared reference file. Anything else deadlocks the main thread when an existing tab navigates (e.g. from the omnibox).
- **Chrome-style-only APIs never reach this Alloy-only app:** `ExecuteChromeCommand` (so Reader mode is a vendored Readability.js transformation, not CEF's dom_distiller) and Chromium's own password-manager UI (hence this app's own password manager). `CefContextMenuHandler`, unlike `CefCommandHandler`, *is* available and is how native context-menu items get added.
- **`CefLifeSpanHandler::OnBeforePopup` must stay overridden.** Without it CEF opens its own raw, non-Swift-owned window for every `target="_blank"` link. It carries no modifier state, so ⌘/⇧-click overrides come from a point-in-time `NSEvent.modifierFlags` read.
- **`CefBrowserHost::SetAudioMuted`/`IsAudioMuted` are real and work.** There is no audible-state *callback*, so the playing indicator is driven by an injected script and a polled marker attribute — not the shared `cefQuery` channel, which has exactly one consumer slot per tab.
- **Never draw anything over a CEF page, even as a later layer-backed sibling.** Whether CEF's surface covers an overlapping AppKit view depends on the rest of the window: link peek's panel rendered above the page while the tab strip was showing and vanished entirely, with nothing logged, once the strip hid for a single-tab window, although the view hierarchy was identical. A feature that must show something where the page is (link peek) takes the page's hostView out of the container and puts a still of it in its place; everything else frames itself beside the content area instead.
- **`NSGlassEffectView` only guarantees z-order for content inside `contentView`.** Real content added as a plain sibling subview renders blurred or vanishes.
- **`--profiles-root` must scope *everything*, not just CEF's cache path.** `session.json`/`profiles.json` go through `ProfilesRootResolver`, and `UserDefaults`-backed preferences through `AppPreferencesStore` — otherwise an "isolated" agent launch silently writes Brady's real settings.
- **The login Keychain is per user, not per `--profiles-root`.** Saved passwords (`PasswordStore`, `kSecAttrSecurityDomain`) and cards (`CardStore`, `kSecAttrService`) are therefore namespaced by `KeychainNamespace` (`Packages/BrowserCore`): empty for the real install (its existing items, no migration) and `-scratch-<hash of the canonical root>` for any other root, placed before the profile name so no profile name can reach another namespace. Any new `SecItem` store must go through it, or a scratch instance reads and overwrites the real items.
- **Per-profile directories are keyed by profile `id`, never name** (`ProfileManager` runs a one-time migration that renames legacy name-keyed directories and skips ambiguous cases rather than guessing).
- **`AF_UNIX` caps `sockaddr_un.sun_path` at 104 bytes.** The CLI socket therefore lives under a short hashed name in the per-user temp directory (`confstr(_CS_DARWIN_USER_TEMP_DIR)`, `/var/folders/.../T/`, mode 0700), not `/tmp`. The socket is 0600, and the server rejects any peer whose uid is not its own. The name is short, the same trick CEF's own `SingletonSocket` uses — nesting it under a deep `--profiles-root` silently disables CLI control entirely.
- **Concurrent `scripts/build.sh` runs serialize on a `mkdir`-based lock in `build/.build-lock`** (macOS ships no `flock(1)`). Two builds against the shared `build/` dir otherwise race Xcode's build database and produce a spurious "database is locked" failure that reads like a real code break.
- **Tab lifecycle is event-driven via `TabLifecycleCenter`,** not discovery timers — a `cefQuery` sent before a poll tick used to be dropped in silence. `TabAudioCoordinator`'s 1.5s timer is a deliberate exception: it reconciles a page state with no native event behind it.
- **Drag-to-reorder runs off a single local `NSEvent` monitor.** A nested `nextEvent` tracking loop is ruled out outright: it would block the same main run loop `BRWMessagePump` drives the engine off.
- **A `WebKitEngine` conformer runs beside `CEFEngine`; each tab picks one.** Most of the `BrowserEngine` surface works; per-tab muting is done in page script, DevTools and responsive design mode lean on private SPI (below), and custom context-menu items and per-tab CPU are confirmed impossible. Passkeys work there only in a build signed with the entitlement and its provisioning profile (see Passkeys above) -- never in an ad-hoc build. `./scripts/test-webkit.sh` runs the real `Engine/WebKit*.swift` adapter against real `WKWebView`s (`Packages/WebKitEngineTests`), with no app build and no CEF.
- **CEF 150 cannot dock DevTools through `CefBrowserHost::ShowDevTools`.** It only builds Chrome-style DevTools browsers, a parent view forces Alloy style on macOS, and an Alloy-style DevTools browser trips a `CHECK` in `browser_host_create.cc` that takes the app down. So docked tools are the real Chrome front-end self-hosted by the bridge in its own browser, talking to the page through a scoped DevTools-protocol bridge (`BRWDevToolsHandler`). It runs without `can_dock`, so it has no dock-side menu, close button or device mode of its own -- the app's pane header and device toolbar supply them (`devToolsHasOwnChrome: false`). A `nil` container still means CEF's own separate DevTools window.
- **WebKit DevTools are the private `_WKInspector` SPI,** docked into the app's container with `_setInspectorAttachmentView:`; the inspector's own dock buttons move it, reported back through `engineTabDevToolsDidRequestDockSide`. Every selector is checked at runtime: if any is missing, the capability turns off and DevTools hands off to Safari's Develop menu instead. **WebKit's responsive design mode is private layout/scale SPI** on `WKWebView`, similarly gated (`WebKitResponsiveDesign.isAvailable`); macOS WebKit has no touch or `<meta name="viewport">` support, so neither can be emulated.
- **Never `codesign --deep`, and never leave broken symlinks in the bundle.** CMake's framework copy creates self-referential `Versions/A/A`-style links that `codesign --verify --strict` accepts but Gatekeeper rejects ("invalid destination for symbolic link in bundle") — `scripts/sign.sh` prunes them before signing. This only ever bites a *downloaded* copy, never a locally built one. **Copy any further framework into the bundle with `ditto`, not CMake's `copy_directory`** — `copy_directory` is what creates those broken links in the first place, and `ditto` reproduces a vendor framework's symlinks faithfully, so Sparkle.framework needs no pruning at all.
- **Sparkle ships four separately-sealed nested code items** — `XPCServices/Downloader.xpc`, `XPCServices/Installer.xpc`, `Updater.app` and the standalone `Autoupdate` tool, all inside its own version directory. `codesign` will not reach any of them on its own, so `scripts/sign.sh` signs them innermost-outward before the framework, which must come last or its seal covers signatures about to be replaced. No entitlements on any of them: those are only needed by a sandboxed host, and this app is never sandboxed.
- **The OSCrypt cookie-encryption key lives in a Keychain item this app cannot rename.** CEF's framework hard-codes the login-keychain item as `service="Chromium Safe Storage"`, `account="Chromium"` (`components/os_crypt/common/keychain_password_mac.mm`) — there is no `CefSettings` field, no command-line switch, and no exported symbol to override it, so every unbranded CEF/Chromium embedder on a Mac shares one item. Renaming it needs a from-source CEF build until chromiumembedded/cef#2692 lands (PR #4247 is still unmerged). Whenever it does become possible, migrate by **copying the existing secret's value into the new item** before the first launch under the new name: a bare rename makes OSCrypt mint a fresh key, and Chromium **deletes** every `v10` row it cannot decrypt on the first load, with nothing in `chrome_debug.log` and no error anywhere. One launch under the wrong key is therefore unrecoverable — restoring the old key afterwards finds an empty table — so the copy has to happen before that launch, not after it.
- **`--use-mock-keychain` derives the key from the literal string `mock_password`,** so a dev build's cookies are encrypted with a publicly known key and are not meaningfully protected at rest. It also means cookies never survive a switch between mock and real Keychain mode in either direction (see `BRWDisableMockKeychain` above) — expect a one-time logout across every site on that transition, not a bug.
- **The vendored Readability.js declares `function Readability(...)`, not `class Readability`,** which is what makes it safe to inject into one page twice. Reader mode and reading-list capture (browser-56p) both prepend the whole library to their own wrapper script, so a page the user reads *and* saves gets two copies in one global scope. A function declaration may be redeclared there; a `class` may not — it throws a `SyntaxError` that takes down the entire script it was concatenated into, wrapper and all, with nothing in the page console anyone is watching. Updating the vendored library to a version that uses `class` would therefore break Reader mode and offline capture at once, with no obvious cause and no compile error. Reader mode has depended on this since it was written, silently.
- **A `data:` URL is capped by Chromium at `url::kMaxURLChars` (2 MiB), and going over it renders a blank window with nothing logged anywhere.** No exception, no console message, no failed-load callback -- the page simply does not appear. This has now bitten two independent features, which is why it is written here rather than in either one's comments: the start page's background image (`StartPageBackgroundImageStore.maxEncodedBytes`, found live -- a 1.37 MB background rendered an empty start page, the same picture at 538 KB rendered fine) and the reading list's offline articles (`ReadingListStore.maximumArticleBytes`). Anything reaching for a `data:` URL as a delivery vehicle has to budget for it, and base64 costs 1.34x, so the real ceiling on the *document* is about 1.57 MB before encoding -- less whatever template wraps it. Both features therefore cap their payload well below that rather than at it.
- **Never order a window on screen while the omnibox has focus** -- not a child window, and not a standalone panel raised by window level either. macOS attaches an out-of-process `NSRemoteView` completion list (`SPCompletionListServiceViewController`) to the focused `NSTextField`, the window-ordering walk tells it about a window that is not its container, and `-[NSRemoteView containingWindowWillOrderOnScreen:]` asserts. The uncaught `NSInternalInconsistencyException` takes down the whole browser. This is why there is no drop-down panel under the omnibox (browser-5kq.10), and why the profile switcher is a key panel opened from a menu item.
- **The app activates itself only through `AppActivation.activate()`,** which does nothing under `--test-no-activate`. A direct `NSApp.activate(ignoringOtherApps:)` in any code path an agent can reach (a routed `browser open`, `--show-settings-tab`, a window controller's `show`) lets a scratch instance take Brady's keyboard, and his typing in another app then lands in the scratch window. This has happened. A scratch launch never reaches the real `NSApp.activate` call inside the helper, so a change to the helper itself needs a normal launch to verify -- a self-recursive helper once shipped that way and hung every real launch.
- **AppKit's own window restoration is switched off in `main.swift`** (`ApplePersistenceIgnoreState`, registration domain only). AppKit keeps one crash history per bundle id, shared by the installed app, every dev build and every scratch instance; after a few `kill`ed test launches it blocks the next launch on a modal "reopen windows?" alert *before* `applicationDidFinishLaunching`, so the engine and the CLI socket never start. With `--test-no-activate` that alert is invisible, and the symptom is only "the CLI can't find the socket". The app restores its session from `session.json` itself.
- **A SQLite file copied out of another app's profile must bring its `-wal` with it and be opened read-write.** WAL mode is recorded in the database header, so a lone copy of a WAL-mode file opened `readOnly` fails as soon as it is queried (found the hard way: the reader just reported "unexpected format"), and even when it opens, the running owner's newest writes -- a password saved a minute ago -- are still sitting in the `-wal` it left behind. `ChromiumProfileReader.withCopiedDatabase` copies both into a 0700 temp directory -- the `-wal` first, since a checkpoint between the two copies is harmless in that order and corrupting in the other -- retries once if the copy will not read, and deletes it afterwards; the copy is private, so opening it read-write is safe. `SafariImportScanner` still copies `History.db` alone.
- **Importing from Chromium browsers never touches plain Chromium's keychain item.** Every Chromium browser keeps its password key in `"<Name> Safe Storage"`, and `ChromiumBrowser.known` deliberately leaves out Chromium itself, because `"Chromium Safe Storage"` is this app's own CEF cookie key (above). On macOS the stored format is `v10` + AES-128-CBC; any other `vNN` prefix is counted as unreadable rather than guessed at.
- **CEF has no two-finger swipe back/forward.** Chromium's history swipe lives in Chrome's browser layer, which an Alloy-style embedder never gets, so `SwipeNavigationController` rebuilds it from a read-only local `.scrollWheel` monitor (never a `scrollWheel` override or a tracking loop -- see `BRWMessagePump`), with `SwipeScrollProbeScript` telling it whether the page would scroll sideways instead. A wheel event over an iframe is dispatched only in the iframe's document, so the main-frame probe can never see it; the probe reports "pointer over a frame" from `pointerover` instead and every swipe that starts there is left to the page. WebKit declares `nativeSwipeNavigation` and uses `WKWebView`'s own gesture.
- **Chrome extensions run only on the WebKit engine (macOS 15.4+, `WKWebExtensionController`), one controller per profile** (`Engine/WebKitExtensions.swift`, UI in `Sources/App/Extensions/`, `EngineCapabilities.webExtensions`; CEF 150 Alloy has no extension system). A tab's web view only gets content scripts if its configuration carried the profile's controller *at creation* -- it cannot be added later -- so `WebKitTab.init` asks `WebKitExtensionManager.configuration(for:profileId:initialURL:)` for every tab. An extension's own page (`chrome-extension://<id>/...`, options pages) only renders in a web view built from `context.webViewConfiguration`, so that is swapped in when a tab *opens* on one; navigating an existing tab there does not work yet. The controller's `webViewConfiguration.applicationNameForUserAgent` must equal the tabs' exactly: WebKit restarts extension workers when the user agent changes and never starts them again. Set `context.baseURL` to a stable `chrome-extension://<id>/` (scheme registered with `MatchPattern.registerCustomURLScheme`), or WebKit picks a random origin each launch and the extension's localStorage/IndexedDB vanish. Only the grants the user agreed to (stored in `<profile>/Extensions/installed.json`) are re-applied on load, never "whatever the manifest asks for today". Load extensions one at a time: started together, WebKit fails some workers and never retries. **Never hand a store package to `ditto` or any second unzipper:** `ZipArchive` extracts it in-process from the one central-directory parse it vetted, because a crafted zip (decoy end record in the comment, a symlink mode under a non-Unix "made by", local names that disagree) reads differently to another extractor, and a signed package could then write through a link outside the extension's folder.
- **A private window's profile id starts with `Profile.privateIdPrefix`, and nothing keyed by it may reach the disk.** The profile is throwaway -- never in `profiles.json` -- so anything written under `<profiles-root>/private-<UUID>/` is both a record of private browsing and an orphan no window can show again. `ProfileDataStoreManager` gives such a profile an in-memory database and `FaviconLoader` skips its disk cache; any new per-profile store must do the same, or refuse to save in a private window.
- **A private tab's cookie jar lives and dies with its engine tab, not its window.** Both engines give every private engine tab its own ephemeral store (`BRWCreateEphemeralRequestContext` per CEF browser, `WKWebsiteDataStore.nonPersistent()` per WebKit tab), so anything that closes and recreates a private tab's engine tab signs it out of everything. This is why tab sleep (`TabSleepCoordinator`) never sleeps private tabs.

- **Both engines share one process, and CEF owns the process.** `BRWApplication` is always `NSApp` (WebKit needs no subclass and runs under it), CEF's external pump and WKWebView's IPC both ride the ordinary main run loop, and quitting is CEF's `-terminate:`: the window close handler closes every tab of either engine, CEF waits for its browsers, then `exit(0)`. `-[BRWApplication terminate:]` posts `willTerminateNotification` itself just before `exit(0)`, after `CefShutdown`, so an observer may flush its own state but must never touch CEF. Every process-wide engine setting goes through `Engines`, which sends it to both.
- **Which engine a tab uses is `EngineSwitchPolicy` (RoutingCore/EngineRules.swift), fed by `EngineRulesStore` (`engine-rules.json`, global, not per profile).** A rule pulls a page into its engine for any navigation; with no rule, a new tab or explicit load gets the default (`--engine` or Settings), but a page's own navigation stays in the tab's current engine, so a ruled site's sign-in or checkout hop keeps its cookies. "Reopen in ..." sets a per-tab override that beats rules on that site. Moving a tab (`Tab.switchEngine`) closes its engine tab and opens a new one at the URL: back/forward history, page state, a POST body (it becomes a GET) and a private tab's cookie jar do not cross. Popups, and tabs with a live popup, never move on their own, because `window.opener` only exists inside one engine tab. Built-in rules send DRM streaming sites to WebKit (this CEF build has no proprietary codecs or signed Widevine); they can be switched off, not deleted.

## browser CLI

A companion terminal tool (browser-82d) for controlling and inspecting a running instance without UI automation -- see the UI verification protocol above; this is the sanctioned way for agents to exercise the app instead. Lives at `browser-cli/` (a standalone SwiftPM package, entirely outside the Xcode/CMake app build), built by `scripts/build.sh` and signed into `Browser.app/Contents/Resources/bin/browser` -- put it on your `PATH` once with `ln -sf ".../Browser.app/Contents/Resources/bin/browser" /usr/local/bin/browser`.

```
browser open <url> [--profile <name>] [--new-window | --little]
browser window new [<url>] [--profile <name>]
browser windows [--profile <name>]
browser focus [<profile>] [--profile <name>]
browser route-test <url> [--from-app <bundle-id>]
browser profiles
browser tabs [--profile <name>]
browser history search <query> [--limit N] [--profile <name>]
browser bookmarks list [--folder <path>] [--profile <name>]
browser page <open|list|snapshot|click|type|press|...> ...   # agent control, see below
```

Every command accepts `--json` for machine-readable output and `--profiles-root <path>` to target a scratch instance instead of the real one (matches the app's own launch argument). **`--profiles-root` must be two separate argv entries** -- anything else (`--profiles-root=/path`, or a single quoted `"--profiles-root /path"` token, which is what zsh's not-word-splitting an unquoted `$VAR` produces) is now a hard error, because the resolver's own fallback for an unrecognised flag is Brady's *real* instance; browser-4xc's own testing opened tabs in his live browser exactly that way. `open`/`profiles`/`tabs`/`window new`/`windows`/`focus` talk to the running app's `CLIServer` socket (`Sources/App/CLI/CLIServer.swift`) and fail with a clear error if no instance is running at that `--profiles-root`; `route-test`/`history search`/`bookmarks list` read `routing.json`/`profiles.json`/a profile's real `browser.db` directly and work with no app running at all. `open` with no `--profile` routes through the same `RoutingCoordinator`/`RuleMatcher` path a real clicked link would (with no attributable source app, so `sourceBundleIds`-scoped rules never match a CLI-issued open); with `--profile`, it bypasses routing rules entirely. `open --new-window` keeps that profile resolution but forces a brand-new window instead of a tab in the profile's frontmost one; `window new` is the no-URL form of the same idea (the start page, regardless of the new-window preference ⌘N uses). `open --little` opens a little window (`LittleWindowController`: one page, "Open in Browser" ⌘O moves the live tab into the profile's normal window without reloading); without it, a routed `open` still honours a matched rule's `openIn`, but not the global "links from other apps" preference. `route-test` is the one built specifically for debugging a rule that silently isn't matching -- it reports which rule (1-based) decided the result, or that the default profile was used, and whether a link from another app would get a tab or a little window (`openIn`/`openInReason`: `rule`, `preference` or `default`).

Never gains a command or field that surfaces passwords/credentials, in any form, even behind `--json` -- a deliberate, permanent scope boundary, not a gap to fill in later.

`raycast-extension/` is a Raycast extension wrapping exactly these commands (browser-4xc) -- switch to a profile, open a link or an empty window in a chosen profile, plus history/bookmark search. It is for every Browser user: anyone installs it from source (`npm install && npm run dev`, which imports it into Raycast and leaves it installed; see its README, linked from `docs/index.html#raycast`). It is prepared for the Raycast Store but **not in it yet** -- `npm run publish` opens a PR on `raycast/extensions` from Brady's own Raycast and GitHub accounts, so only he runs it. It finds the CLI inside `Browser.app` in `/Applications` or `~/Applications` with no `ln -sf`, and it can be newer than the installed app (Switch to Profile needs `browser focus`, which postdates 0.1.0), so a CLI command it starts relying on must ship in a release first.

### Agent control: `browser page`

`browser page help` lists the commands. An agent opens its own window in a chosen profile (`page open <url> --profile <name>`, or `--private` for an empty cookie jar), gets a short id (`p1`), and then reads it (`snapshot`, `eval`), acts in it (`click`, `hover`, `type`, `press`, `select`, `scroll`, `navigate`, `wait`), captures it (`screenshot`, `record start|stop`) and closes it. `Sources/App/CLI/AgentPages.swift` holds the commands, `AgentPageScript.swift` the page-side snapshot/ref/target script, and the engine side is `EngineTab.automation` (`EngineCapabilities.agentControl`, read per tab): `Engine/DevToolsProtocolAutomation.swift` for CEF, through `BRWAutomationChannel` on the tab's own DevTools session, and `Engine/WebKitAutomation.swift` for WebKit.

- **Off unless Brady turns it on** -- Settings > Privacy > Agents (`AgentControlPreference`), or `--allow-agent-control` on the app's own command line. The CLI can never turn it on.
- **Only windows `page open` created** are reachable, never the user's own. Those windows never take a routed link, a menu command or Handoff, and are never saved in the session (`WindowManager.markAgentOwned`). A page in one that opens a new window gets a new tab in the same agent window instead. The password manager never fills them.
- **An agent page never changes engine.** The engine rules pick its engine when it opens (so a page opened on a WebKit-ruled site starts in WebKit), and from then on its tabs hold that engine (`TabDelegate.tabHoldsEngine`, `Tab.holdsEngine`): no rule, `page navigate` or "Reopen in ..." moves them, because the automation drives the engine tab itself and a move would close it mid-command.
- **An agent window's layout is fixed:** the horizontal tab strip, always shown, whatever the layout preferences say, so the sidebar never reveals on hover and the page never resizes under the agent. Its omnibox never takes focus.
- **Input never goes through the OS,** so it works with the window in the background or off screen and never moves the pointer, takes the keyboard or activates the app. Opening the window does not activate the app either (`openNewWindow(activateApp: false)`). CEF uses DevTools `Input.*` with focus emulated. WebKit gets real AppKit mouse-down/up and key-down/up events handed straight to the web view (`WebKitAutomation`), so the page sees trusted events with their default actions, and the private `_doAfterProcessingAllPendingMouseEvents:`/`KeyEvents:` hooks hold the command until the page has handled them. A temporary responder after the web view takes the commands an unhandled key sends up the chain (Escape's `cancelOperation:`, a beep's `noop:`). WebKit drops mouse moves while the window is not key, so hover is DOM events from page script and CSS `:hover` menus do not open. Text goes in with `execCommand('insertText')`.
- **Agent windows never become key** (`BrowserWindowController.agentPresentation`), so they never take the user's typing. `page open --headless` parks the window off every screen, out of the Window menu and Mission Control. `page show`/`hide` move it on and off screen; `page show --focus` is the one way an agent window takes the keyboard, for when the user has to sign in by hand.
- **A page whose window closes stays known** (`AgentPages.closedPages`): the next command on it says when it closed and the last URL a command saw, instead of "No agent page". Nothing in the app routes a navigation inside an agent page to another profile -- routing only ever applies to links arriving from outside (`RoutingCoordinator.route`), and a popup it opens becomes a tab in its own window (above) -- so a page that vanished was closed by the page itself (`window.close()`), by its last tab closing, or by the user.
- **`page eval` takes an expression or statements.** It is run as an expression first; on a `SyntaxError` it is run again as the body of an async function, so `a(); return b` works and a returned promise is awaited either way. Output has no escaped slashes, and `--raw` prints a string result as plain text.
- **`--wait-idle`** (open/navigate/reload/click/type/press, and `wait --idle`) means no fetch/XHR in flight and no DOM mutation for 500 ms (`AgentPageScript`'s `idle`). The page script patches `fetch` and `XMLHttpRequest.prototype.send` to count in-flight requests, which is why it installs on the first command in a document, before any click; a drawn cursor's own mutations are ignored.
- **`--text` targets rank matches**: a real control (link, button, menu item, field) beats a clickable generic or table cell, and a heading comes last; `--role` narrows to one role, and the result says "(1 of N matches)" when several matched. Hover reports the element's `title`/`aria-describedby`/`aria-keyshortcuts`, since the engine draws the tooltip outside the page and no screenshot captures it; snapshots show `title=` and `shortcut=` when present.
- **Chords type what the user's layout types** (`Engine/MacKeyboardLayout.swift`, `UCKeyTranslate` on the current input source): `press 2 --modifiers alt` delivers "™" on a US layout, as a real Option+2 would, on both engines. Cmd/Ctrl chords keep the plain character, as AppKit reports for a shortcut.
- **Dialogs and file choosers never show in an agent page** (`EngineTabAutomation.dialogHandler`, WebKit only): alerts close, confirm/prompt follow `page dialogs <id> accept|dismiss` (dismiss by default), and the next command reports each one. `page upload` gives files to the chooser its click opens, never from the app's own data or the keychains. Same-origin iframes are walked like shadow roots; cross-origin ones cannot be reached.
- **WebKit stops painting a covered or off-screen view,** which freezes the drawn cursor and leaves screenshots and recordings stale. `WebKitAutomation.prepare` turns off the agent web view's occlusion detection (private `_setWindowOcclusionDetectionEnabled:`, checked at runtime). WebKit screenshots are `takeSnapshot`, which only ever sees the viewport, so `--full-page` there scrolls the window a viewport at a time and stitches the strips (`WebKitAutomation.fullPageScreenshot`, capped at 20 viewports, stops when the page will not scroll further): content fixed to the viewport repeats once per strip, and a page that scrolls inside an inner element gives the viewport alone. Its recording is snapshots at 15 fps. The scroll step waits on a timer, never `requestAnimationFrame`, which a view that is not drawing never gets.
- **Password fields:** `type`, and `press` with a character key, refuse when the target or focused field is `type=password`. A snapshot never carries a password field's value. `eval` runs any script in the page, so the opt-in setting is its only guard.
- **Recording** is a screencast: JPEG frames when the page repaints, plus `frames.ffconcat` holding each frame for as long as it was shown, so ffmpeg makes a real-time video. `--cursor` draws a pointer in the page where clicks land; synthetic input has none of its own.
